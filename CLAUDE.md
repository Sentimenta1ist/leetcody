# LeetCode Practice — заметки для Claude

Личный проект подготовки к алгоритмическим интервью (ориентир — асинхронный тест на несколько задач
разной сложности + живой скрининг с парой задач на 20 минут каждая). Не production-код, все решения
намеренно в одном классе.

## Структура проекта

- `src/main/java/com/Main.java` — **все** решения и JUnit-тесты лежат в одном классе `Main` (сознательное решение
  пользователя, не предлагать разносить по файлам/пакетам).
- `src/main/java/com/ListNode.java`, `LinkedListUtils.java` — вынесенные наружу тип `ListNode` и хелперы
  `buildList(int[])` / `toArray(ListNode)` для linked-list задач. Только вспомогательные структуры/утилиты
  выносятся отдельно, сами решения — нет.
- `src/main/java/com/TreeNode.java`, `TreeUtils.java` — аналогично для деревьев: `buildTree(Integer[])` /
  `toArray(TreeNode)` в LeetCode level-order формате (с `null` для отсутствующих детей, `Integer[]`, не
  `int[]`), плюс `printTree(TreeNode)` — визуальный принт дерева сверху вниз с ветками `/` и `\`
  (алгоритм с рекурсивным построением строк по ширине поддерева, не наивная фиксированная сетка).
  `toArray`/`buildList`/`buildTree` одноимённы между `LinkedListUtils` и `TreeUtils`, но статические
  импорты обоих одновременно компилируются нормально — Java резолвит по типу аргумента.
- `pom.xml` — Surefire сконфигурирован нестандартно: `testClassesDirectory` указывает на `target/classes`
  (не `target/test-classes`), плюс явный `<include>**/Main.class</include>`, потому что тесты лежат в
  `src/main/java`, а не в `src/test/java`. Без этого `mvn test` тесты в `Main` тихо пропускает.
  Зависимости: `junit-jupiter` и `junit-platform-launcher` запинены на `5.10.2`/`1.10.2` (не `RELEASE`) —
  версия `RELEASE` вызывала `NoSuchMethodError` при запуске тестов из IntelliJ (несовпадение версий
  platform-launcher между IDE и Maven).
- `README.md` — таблица прогресса **по паттернам**, не по конкретным номерам задач. Задача в колонке
  "Референс" — просто пример паттерна; если пользователь решил другую задачу того же паттерна, это
  засчитывается — отмечать ✅ и вписывать реальное название в "Что решил". Используются emoji `⬜`/`✅`
  и `🟢/🟡/🔴` для сложности вместо `- [ ]` — GFM-чекбоксы не рендерятся внутри ячеек таблицы.
- `PATTERNS.md` — шпаргалка с шаблонами кода по темам, в порядке плана изучения ниже.
- `SOLUTIONS.md` — лог уже решённых задач: чистый код + краткое описание подхода. Обновлять при каждой
  новой закрытой задаче.

## План изучения (текущий порядок, задан пользователем)

1. **Деревья** — сейчас в фокусе, начинать с простых (раньше хорошо получались, сейчас подзабыты)
2. Массивы / хеш-суммы
3. Графы
4. Стек
5. Бектрекинг
6. Гриди
7. ДП — в конце

Периодически, между темами, возвращаться к одной задаче из уже пройденного пула (см. `README.md`), чтобы
не забывать. Минимальная цель — закрыть все паттерны из `README.md` (или эквивалентные задачи того же
паттерна, не обязательно те же номера).

## Как предпочитает работать пользователь

- **По умолчанию — подсказка, не разбор.** Если явно не просит "объясни" или не написал прямым текстом,
  что не может понять/застрял — давать 1-3 предложения намёка, не полное решение и не лекцию.
- **Если после 2-3 подсказок всё ещё не понимает** — не продолжать абстрактными подсказками, переходить
  к конкретной трассировке по шагам (значения переменных на каждой итерации), это то, что реально
  срабатывает для этого пользователя, а не ещё один уровень намёка.
- **Если просит явно "покажи решение" / "объясни" — тогда полный разбор ок**, не нужно снова спрашивать
  разрешения.
- Не продолжать объяснять дальше того, что попросили — если после ответа говорит "не надо объяснять,
  я не просил", это сигнал сократить будущие ответы до сути.
- Тесты пишет/просит писать в стиле, который уже есть в файле: простые `assertEquals`/`assertArrayEquals`
  в одном `@Test`-методе, без `@BeforeEach`/параметризации/фреймворков поверх JUnit.
- Минимум абстракций и файлов: один класс на все решения+тесты — осознанный выбор, не "забыли отрефакторить".
- Если пользователь сам пишет код с багом — не соглашаться, что "всё верно", если тесты падают; сразу
  проверять реальным прогоном (`mvn test`), а не только чтением кода.
- Использует нецензурную лексику как обычную речь, без негативного адресата — не реагировать на это
  как на грубость, отвечать по существу.

## Тестирование

```
mvn test
```
из корня проекта. Если правили `pom.xml` или добавляли новый класс — на всякий случай `mvn clean test`,
чтобы не словить закэшированный `.class` от предыдущей (иногда некомпилируемой) версии файла.
